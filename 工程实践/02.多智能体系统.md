# 多智能体系统（Multi-Agent System）

### 1、为什么需要Multi-Agent

单 Agent 类比于一个人什么都会做，但都不是很专业；

多 Agent 每个 Agent 都更加专业（Prompt 高度专业化），分工明确，各司其职，协作完成复杂任务。


核心优势：

- 分工明确：每个 Agent 专注于自己的专业领域
- 并行执行：多个 Agent 可以同时工作
- 错误隔离：一个 Agent 出错不影响整体
- 专业化 Prompt：每个 Agent 可以用领域最优提示词


经典场景：

- 软件开发周期（需求 - 设计 - 开发 - 测试 - 部署）
- 内容生产（调研 - 写作 - 编辑 - 发布）
- 投资分析（宏观分析 - 行业分析 - 公司分析 - 风险评估）


三种经典架构

| 架构 | 特点 |
| --- | --- |
| 协作式 | 多 Agent 平等对话，共同决策；AutoGen 的 GroupChat |
| 分层式 | 上级 Agent 委派任务给下级 Agent；CrewAI 的 Crew+Task |
| 竞争式 | 多 Agent 各自生成方案，择优选择；辩论式 Agent |

### 4、Multi-Agent 的设计原则

1、职责单一：一个 Agent 只做一件事，不要给 Agent 塞太多职责

2、通信标准化：Agent 之间通信用JSON/XML结构化通信，避免自然语言模糊

3、错误隔离：单个 Agent 发生错误不会影响整个系统崩溃，设置重试机制和降级策略

4、可观测性：记录每个 Agent 的输入/输出耗时，便于调试和优化

5、成本控制：用缓存、batching、模型分层来降低成本


Multi Agent 比单 Agent 好在哪？什么时候不该用？

好在：

- 多 Agent 职责单一，单个 Agent 可更加专业化，输出质量更高
- 多 Agent 复杂任务并行执行，效率高
- 系统更模块化、易维护

不适用于：

- 简单任务 （杀鸡不要用牛刀）
- 成本敏感场景（多倍 Agent 调用）
- Agent 间协调开销 > 实际收益

如何处理多 Agent 的冲突和一致性问题


一、常见的冲突类型

| 冲突类型 | 场景 | 举例 |
|---|---|---|
| **任务分配冲突** | 多个 Agent 抢同一个任务，或都认为"不是我的活" | 两个客服 Agent 同时回复同一个用户 |
| **输出矛盾** | 两个 Agent 给出不一致的结论 | 财务 Agent 说利润率 15%，运营 Agent 说 20% |
| **状态冲突** | 共享状态被并发写坏 | 两个 Agent 同时更新同一个订单字段 |
| **循环/死锁** | Agent 之间互相推任务不收敛 | 主管 → 专家A → 主管 → 专家A → 无限循环 |

 二、冲突处理的 5 个工程手段

1. 单调度者模式（Supervisor / Orchestrator）

**不要让 Agent 之间直接通信**，所有调度都走一个仲裁者：

```
用户 → Supervisor（唯一仲裁者）
           ↓ 分发给谁？
   ┌──────┬──────┬──────┐
专家A   专家B   专家C   检索Agent
   └──────┴──────┴──────┘
           ↓ 结果汇总
       Supervisor 统一输出
```

- 任务分配冲突不存在，因为只有 Supervisor 说了算
- 输出矛盾由 Supervisor 统一裁决（对比冲突、追问冲突源、或让更高权重的 Agent 再审一遍）
- 你项目 experience 里踩过的坑就是**专家回 Supervisor 后重复选同一专家造成死循环**，解决办法是在状态里加 `visited_experts: list[str]` 或 `next_node: str`，Supervisor 选过的专家不再选第二次

2. 共享状态加锁 + 版本号

多 Agent 写同一个对象（订单、文档、数据库行）会写坏：

```python
# 乐观锁（版本号）
update document
   set content = ?2, version = version + 1
 where id = ?1 and version = ?3
# 如果影响行数 = 0，说明期间被别人改了，重读后重试
```

或者用 LangGraph 的 `add_messages` 这种**只追加不修改**的数据结构，天然避免并发写坏（消息是 append-only 的，后面的消息可以 override 但前面的不被覆盖）。

3. 仲裁机制：权重 + 投票 + 最终裁决人

输出矛盾时，不是随机选一个：

```
问题：公司全年利润率是多少？
  财务Agent：15.2%（权重 10/10，直接数据源是财务系统）→ ✅ 采纳
  运营Agent：20%  （权重 6/10，数据是手工统计）
  CEO Agent：我再确认一下（权重 ∞，人类或高权限 Agent 一票否决）
```

实现方式是**每个工具/Agent 返回结果时附带 confidence 分数**，Supervisor 取加权综合。

4. 任务幂等 + 去重 ID

两个 Agent 同时跑同一件事（比如发邮件、扣库存），会执行两次：

> 每次任务生成唯一 `job_id`，执行前查 Redis `SETNX job:done:{job_id}`，拿到锁的才干活，没拿到的直接跳过。

这样即使 Supervisor 重复派发也只会执行一次。

5. 显式收敛路径（防止死循环）

LangGraph 里 Agent 最容易出的 bug 就是无限循环。工程上的硬性约束：

```python
state = {
    "messages": [...],
    "turn_count": 0,          # 轮次计数器
    "max_turns": 10,          # 硬上限，到了强制总结或报错
    "visited_agents": [],     # 已经跑过的 Agent，不重复
}

# Supervisor 路由逻辑
if turn_count >= max_turns:
    return "SUMMARY"          # 强制收束到汇总节点
if next_agent in visited_agents:
    return "SUMMARY"          # 重复选择也收束
```

你 experience 里从 "专家→主管→专家" 改成 **"专家→summary→END"**，就是用收敛路径解决死循环。

三、一致性保证的两个层次

弱一致（大多数 RAG 场景够用）
各 Agent 拿到的数据可能有微小时差，但最终结果正确就行。典型做法：
- 工具调用前查最新数据，不缓存中间态
- Supervisor 最后一步做 cross-check："结论 A 和结论 B 是否自相矛盾？"

强一致（金融/订单/扣库存）
必须保证所有 Agent 看到的是同一份数据，并且状态不被并发写坏：
- 共享资源用数据库事务 + 乐观锁
- 只允许一个 Agent 写同一个实体（按领域拆写权限：订单 Agent 只改订单表，支付 Agent 只改支付表）

四、面试一句话答法

> 多 Agent 冲突靠四层架构解：**单 Supervisor 仲裁**（解决分配冲突和输出矛盾）、**乐观锁/幂等 ID**（解决状态写坏和重复执行）、**显式收敛路径 + 轮次上限**（防止死循环）、**加权裁决**（解决结论冲突）。工程上最容易踩的坑是忘记维护执行进度导致 Agent 间互相调用无限循环，必须在状态里显式存 `turn_count` 和 `visited_agents`，并保证图上有确定性的 END 路径。
