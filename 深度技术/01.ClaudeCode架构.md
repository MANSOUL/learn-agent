# Claude Code 架构剖析

### 1、整体结构

Layer 1: 用户界面层（UI Layer）

- CLI
- VS Code 插件
- Web UI
- Claude Agent SDK


Layer 2: Agent 核心调度层（Core Scheduling Layer）

- Agent Loop：模型响应与工具结果的迭代循环
- Steering Queue：接收中途补充或纠偏指令
- Stream Gen：流式输出管理
- Tool Engine：工具调用编排器
- Context Compaction：上下文压缩


Layer 3: 工具执行与管理层（Tool Execution Layer）

- Bash/Grep/View/Edit/Write 等基础工具
- Task 工具 -> SubAgent 创建与管理
- MCP 工具集成（连接外部 MCP Server）
- 权限与安全控制（Permission）


Layer 4: 存储与持久化层（Storage & Persistence）

- TODO 列表（短期任务管理）
- Markdown 文件（长期项目记忆）
- Git 集成（diff-based 工作流）
- 会话状态持久化


核心理念：【做简单的事】--- Markdown 代替数据库、正则代替向量检索、单线程代替并行、平面消息代替复杂线程。



### 2、主 Agent 循环

```
while(tool_calls in response):
    tool_call
    send result to llm
return final_result
```

也是 ReAct 循环；

Claude Code 的设计遵循其核心理念：

1、【单线程主循环】--- 不是多 Agent 同时跑

- 原因：可调试性 > 并发性能
- 一个线程、一个消息列表、一条执行路径
- 出问题时，可以从头到尾跟踪每一步


2、【平面消息列表】--- 不是复杂的线程/层级结构

- 原因：LLM 对平面结构的理解最稳定
- 不构建复杂的树形消息结构


3、【做最简单的事】 --- 始终选择实现成本最低的方案

- 搜索代码用 Grep（正则）而不是 Embedding（向量）
- 存记忆用 Markdown 文件而不是数据库
- 这些选择时系统更易理解、更易调试

### 3、实时 Steering 机制 --- 让人可以中途介入

大多数 Agent 的工作模式是：提交任务 -> 等待 -> 输入结果；

在等待的过程中，无法再提交补充内容，若有补充则需中止重来。

Claude Code 引入 Steering 队列改变这一点：

实现原理：

- UI 与 Agent 循环之间维护一个异步待处理队列；
- Agent 等待模型或工具结果时，队列依然可以接收用户消息；
- 当前【安全边界】结束后，循环读取待处理任务；
- 如果有，将新指令注入对话，Agent 无缝调整。


```python
class SteeringQueue:
  def __init(self):
    self._active_buffer = []
    self._pending_buffer = []
    self._lock = asyncio.Lock()

  async def push_user_message(self, msg):
    # 用户中途发消息（非阻塞）
    async with self._lock:
      self._pending_buffer.append(msg)

  async def drain_pending(self):
    # Agent 在每步结束后消费待处理结果
    async with self._lock:
      # 原子性交换两个缓冲区
      self._active_buffer, self._pending_buffer = self._pending_buffer, []
    msgs = self._active_buffer
    return msgs

# Agent 循环中使用 SteeringQueue
async def agent_loop_with_steering(user_input, steering_queue):
  messages = [...]
  while True:
    # 检查用户是否有中途介入
```

### 4、上下文压缩

上下文压缩是长任务保持可继续执行的一类关键技术。


核心机制：

- Context Compactor 监控 输入预算 和 工具输出增长
- 在预留响应、工具结果和安全余量后触发压缩
- 压缩器调用模型将 早期消息 生成【对话摘要】
- 将 早期消息 移除，替换为摘要
- 将重要信息移动到 Markdown 文件（实现长期记忆）


阀值如何定？

- 压太早：增加调用次数，可能丢失细节
- 压太晚：没有空间放响应和工具结果
- 应该把 响应上限、工具最大输出纳入预算


Markdown 对 LLM 友好；且人类可读；零依赖，无需额外基础设施。

压缩前：[system][user][assitant][tool][assitant][tool][...]

压缩后：[system][summary][最近N轮对话]

被压缩的内容：生成 summary、重要信息写入 markdown、不重要的细节直接丢弃

```python
def context_compaction():
  MAX_TOKEN = 100000
  THRESHOLD = 0.8 # 超出 阀值 开启压缩

  messages = [
    {"role": "system", "content": "你是一个专业的xxx..."},
    {"role": "user", "content": "帮我分析xxx..."},
    {"role": "assistant", "content": "好的，让我分析一下xxx"},
  ]

  # 模拟消息
  for i in range(20):
    messages.append({"role": "assistant", "content": f"调用工具分析 {i}..."})
    messages.append({"role": "tool", "content": f"{i} 的结果是..."})

  current_tokens = len(str(messages)) // 4
  usage_pct = current_tokens / MAX_TOKENS

  if usage_pct > THRESHOLD:
    # 触发压缩
    system = messages[0:2]
    recent = messages[-5:]
    middle = messages[2:-5]

    summary = f"【压缩摘要】共 {len{middle}} 条消息，主要内容：分析了xxx，..."

    compact = system + [{"role": "system", "content": summary}] + recent

    new_tokens = len(str(messages)) // 4
    new_usage_pct = new_tokens / MAX_TOKENS
```



### 5、分层 Multi-Agent 架构 --- Task 工具与 SubAgent

Claude Code 的多 Agent 是通过 Task工具 实现的：

- 主 Agent 调用 Task 工具创建 SubAgent
- SubAgent 在独立上下文中运行
- SubAgent 在完成后返回结果
- 主 Agent 合成结果


可复用的设计原则：

1、上下文过滤

- SubAgent 之获取完成任务所需的最小上下文
- 用任务合同显式描述输入、输出和验收条件
- 节省量与质量影响必须在真实任务集上测量

2、工具权限控制

- 研究型 SubAgent：只读权限
- 实施型 SubAgent：完整权限
- 权限通过 SubAgent 创建时动态配置

3、并发限制

- 并发数量应由资源、写冲突概率、权限和可观测性共同决定
- 对同一工作区写入时尤其需要隔离、锁和串行


```python
def create_subagent(task_desc: str, task_prompt: str, avail_tools: list, permission: dict):
  # 构建 subagent 专属系统提示词
  system_prompt = (
    "你是一个定制的子智能体。\n"
    f"任务是: {task_desc}。\n"
    f"可是使用这些工具: {t.name for t in avail_tools}。\n"
    f"你拥有这些权限: {permission}。\n"
    "规则如下:"
    "- 你是无状态的，一次性完成任务"
    "- 清晰的返回你执行的结果"
    "- 不要询问以上说的这些问题"
  )

  # 构建 sub agent 对话
  sub_messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": task_prompt},
  ]

  # sub agent 执行自己的循环
  result = run_agent_loop(sub_messages, tools=avail_tools)

  # 返回结果给 主 agent
  return {"sub_agent_result": result}
```

### 6、Claude Agent SDK

核心理念：给 Claude 一台电脑，让它能自主读写文件、跑命令、搜代码

- 内置工具（文件读写、执行终端命令、查找文件、正则搜索文件内容、所有网络信息、分析网页内容）
- 钩子系统（工具调用前后、有通知、用户提交prompt）
- SubAgent（任务并行、上下文隔离）
- MCP（支持连接MCP服务器）
- 权限管理（default-默认｜提示用户确认，acceptEdits-自动接受文件编辑，plan-规划模式，适合需要审批的工作流）
- 会话管理（多轮对话上下文自动维护、session持久化、session forking）
- 上下文压缩（长任务上下文自动压缩，基于 Claude Code /compact 命令）
- 结构化输出
- ...



### 7、设计原则总结

- 简单之上（主agent循环、markdown代替数据库、正则代替向量）
- 工具优先（agent能力边界=工具的能力边界）
- 可控自主（不追求完全自主追求可控的自主）
- 上下文工程（压缩、阀值、记忆）

Claude Code架构的特别之处：

- 单线程（简单可追踪）主循环 - 实时转向 - 上下文压缩 - 分层 SubAgent
- 设计哲学：做简单的事（工具优先、架构从简）
- 不给 LLM 过多的选择，控制在可预测的路径上

### 8、总结

1. 4层架构：用户交互 → Agent 核心调度 → 工具执行 → 存储持久化
2. Agent 主循环：简洁的 while(tool_calls) 循环，平面消息便于追踪
3. Steering：异步消息队列允许用户在安全边界补充或修正指令
4. Context Compaction：按预算和保真度策略压缩早期对话
5. SubAgent：通过任务工具创建，独立上下文并受权限与资源上限约束
6. Claude Agent SDK：给 Claude 一台电脑，构建通用 Agent

重点在上下文管理和工具设计，不在复杂的 Agent 编排
